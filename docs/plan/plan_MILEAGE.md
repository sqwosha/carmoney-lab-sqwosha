# План: проверка пробега для решения по заявке

`docs/setup/code_map.md` отсутствует в рабочем дереве, поэтому план составлен по фактической структуре и текущему коду. Перед реализацией его нужно сверить с картой кода, когда она появится.

## Файлы

- `backend/config/rules.php` — добавить в секцию `vehicle` конфигурируемый порог пробега для направления заявки на `review`, не заменяя существующий `max_mileage_km`.
- `backend/src/Domain/AssessmentService.php` — передать нормализованный пробег в выбор решения либо применить правило принудительного `review` после LTV-расчёта согласно согласованному приоритету правил.
- `backend/src/Domain/DecisionEngine.php` — расширить ответственность/интерфейс выбора решения для учёта порога пробега либо оставить LTV-движок неизменным, если override будет реализован в сервисе оценки.
- `tests/Unit/AssessmentServiceTest.php` — добавить тесты итогового решения и нулевого лимита для пороговых значений пробега.
- `tests/Unit/ApplicationValidatorTest.php` — зафиксировать поведение пустого или отсутствующего `mileage` и сохранение верхней границы `max_mileage_km`.

## Шаги

1. Сверить план с `docs/setup/code_map.md`, когда файл будет доступен, и подтвердить, что точка выбора решения остаётся в `AssessmentService`/`DecisionEngine`.
2. Добавить в `backend/config/rules.php` отсутствующий отдельный порог `400000` км для бизнес-правила `mileage > порог → review`; не менять `vehicle.max_mileage_km = 500000`, поскольку это независимая граница допустимости входных данных.
3. Определить и реализовать единую точку принятия решения, которая получает LTV и нормализованный пробег: значения до и включая порог используют действующие LTV-правила, а значение строго больше порога направляется в `review`.
4. Сохранить текущий порядок обработки: сначала `ApplicationValidator` отклоняет невалидный пробег, включая значение выше `max_mileage_km`, затем сервис расчёта выбирает решение для валидной заявки. Обеспечить, что у `review` сохраняется `approved_limit = 0`.
5. Не менять формулу LTV, HTTP-контракты, схему БД и репозиторий: пробег уже нормализуется, передаётся и хранится как обязательное целое число.
6. Уточнить обработку пустого/неизвестного пробега и при необходимости исправить валидатор и клиентскую сериализацию: сейчас пустая строка приводится к `0`, а отсутствующее поле и `null` дают HTTP 422. Вносить такое изменение только после решения заказчика.
7. Обновить unit-тесты на уровне сервиса оценки и валидации, затем выполнить `make test` и `make lint`.

## Тесты

- Добавить отсутствующие тесты границы правила `mileage > 400000` при LTV в зоне `approve`:
  - `mileage = 399999`: решение остаётся `approve`, лимит равен запрошенной сумме;
  - `mileage = 400000`: решение остаётся `approve`, так как правило применяется только при значении больше 400000;
  - `mileage = 400001`: решение становится `review`, лимит равен `0`.
- Пустой пробег: зафиксировать согласованное поведение отдельным тестом; текущая прямая передача `""` и пустое поле штатной формы преобразуются в `0`, а отсутствующий ключ или `null` отклоняются с ошибкой `mileage`.
- `mileage = 500000`: заявка остаётся валидной и получает решение по новому правилу пробега.
- `mileage = 500001`: сохраняется HTTP/доменная ошибка валидации по `max_mileage_km`, без расчёта решения.
- Сценарий `mileage > 400000` и LTV выше `review_max`: проверить решение в соответствии с отдельно согласованным приоритетом правила пробега над LTV-отказом.
- Выполнить полный набор PHPUnit через `make test` и синтаксическую проверку через `make lint`.

## Риски

- `max_mileage_km = 500000` — существующее правило валидации. Его замена на `400000` неверно превратит заявки с пробегом `400001–500000` из `review` в ошибку валидации; порог решения должен быть отдельным.
- В текущем коде `DecisionEngine::decide()` принимает только LTV. Изменение его сигнатуры затронет unit-тесты и все будущие вызовы; реализация override в `AssessmentService` уменьшит этот охват, но разделит правила выбора решения между классами.
- Формулировка «иначе решение review» конфликтует с действующим `reject` при LTV выше `85`: без согласованного приоритета нельзя определить, должен ли большой пробег понижать `reject` до `review` или действовать только вместо `approve`.
- Пустая строка в API и пустое поле браузерной формы сейчас не считаются отсутствующими: они приводятся к нулевому пробегу. Изменение этого поведения может стать несовместимым изменением API и интерфейса.
- Текущий `ApplicationValidator` приводит произвольные значения к `int`; дробный, строковый либо некорректный ввод может нормализоваться неявно. Усиление типовой валидации не входит в задачу, если не будет отдельно согласовано.
- Не входят: изменение формулы LTV, изменение порогов LTV, пересчёт лимита, миграции БД, изменение схемы хранения, массовое исправление сохранённых заявок и ввод новых ограничений на frontend.

## Вопросы, на которые без заказчика не ответить

1. При пробеге больше 400000 км и LTV выше `85` итоговое решение должно быть `review` (правило пробега перекрывает `reject`) или `reject` (LTV имеет приоритет)?
2. Что считать пустым/неизвестным пробегом: отсутствие ключа, `null`, пустую строку, пробельную строку и значение, не приводимое к целому; должно ли каждое из них давать ошибку валидации или иной результат?
3. Нужно ли изменять frontend, чтобы пустое поле не сериализовалось как `0`, и требуется ли текст подсказки/ошибки для нового порога?
4. Должно ли правило пробега применяться только к новым расчётам или также к просмотру/повторной оценке уже сохранённых заявок?
